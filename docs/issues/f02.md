# Implement user registration

Local planning ID: F02. This is not a GitHub issue number.

Suggested priority: P0. Type: feature.

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.

## Goal

Create a global User with safe password storage and canonical-email uniqueness.

## Scope

- POST /users with only email/password; reviewed validation and normalization; maintained hashing library and reviewed hashing policy.
- Commit User before returning 201 UserProfile; server controls User ID and active state.

## Out of scope

- Login, token issuance, memberships, email verification/delivery.

## Acceptance criteria

- Store canonical email and password hash, never plaintext. Responses/errors exclude plaintext/hash/secrets.
- Reject extra/missing/invalid fields with 422 validation_error. Create no Organization or Membership.
- Duplicate email maps only the known uniqueness violation to the contract response; unrelated persistence failures are not duplicate-email conflicts.
- Failed insertion/commit returns no success and leaves no new User.

## Expected tests or review evidence

- Valid registration, hash verification using the original password and library, safe response projection.
- Missing/invalid inputs; injected user_id/is_active/role are rejected.
- Coordinate two overlapping attempts with independent sessions: one 201, one documented conflict, one persisted User. Join both before cleanup. Verify constraint/error mapping independently.
- Insertion and commit failure rollback; separate persisted-state verification.

## Implementation evidence — 24 September 2026

The current feature branch implements strict `POST /users` input, shared canonical
email and password normalization, pwdlib Argon2id hashing, a transaction-owning
registration service, and SQLAlchemy persistence. Only the named `uq_users_email`
constraint becomes `409 email_already_exists`; unrelated persistence errors retain
their server-error behavior. The success response projects only `user_id`, canonical
`email`, and `is_active`.

Unit and HTTP tests cover boundary validation, injected-field rejection, password
preservation and verification, service ordering, insertion/commit rollback, response
safety, and duplicate behavior. PostgreSQL tests verify fresh-session persistence,
stored hash verification, absence of Organization/Membership side effects, named and
unrelated constraint handling, and HTTP-to-database round trips. The full local checks
passed with 147 non-integration tests and 66 PostgreSQL integration tests.

The final local acceptance test passed on 26 September 2026: two HTTP attempts used
independent Sessions and synchronized before insertion, both joined before cleanup,
and produced one 201, one controlled 409, and exactly one persisted User. The stored
hash verified only the winning password. The registration file now passes seven tests.
The final merge-candidate run passed 147 non-integration tests with 69 database/schema
tests deselected and all 67 ordinary PostgreSQL integration tests. Hosted CI,
pull-request review, merge, and GitHub issue closure remain pending; this local evidence
alone does not mark #11 complete.
