# Implement shared API errors and safe request logging

Local planning ID: Q02. This is not a GitHub issue number.

Suggested priority: P0. Type: infrastructure.

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.
Status: awaiting user review; not implemented or published.

## Goal

Provide consistent public failures and useful request diagnostics without leaking sensitive data.

## Scope

- Shared exception mapping/validation envelope and request logging/correlation handling per D03.
- Reusable components consumed by feature endpoints, without implementing their business permission checks.

## Out of scope

- Logging platform, distributed tracing service, operational dashboards, business authorization implementation.

## Acceptance criteria

- Expected typed failures map to the finalized HTTP/code/envelope; unknown server failures return generic safe output.
- Preserve required headers such as bearer authentication challenges. Never turn all DB errors into duplicate-email or authentication failures.
- Request diagnostics include the reviewed correlation fields and bounded metadata; exclude credentials, request bodies, Authorization headers, full URLs with secrets, and raw tokens.
- Validate or replace untrusted correlation inputs per contract; failures are traceable without public SQL or stack traces.
- Startup configuration failures remain safely reported even before request middleware exists.

## Expected tests or review evidence

- Validation, business and unexpected exception mappings; required headers; correlation propagation/generation and hostile values.
- Synthetic password/token/connection URL does not appear in captured public errors or application logs; correct failures remain observable.
- Use bounded test-only routes or helpers rather than inventing public product endpoints.
