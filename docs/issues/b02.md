# Establish guarded PostgreSQL integration tests

Local planning ID: B02. This is not a GitHub issue number.

Suggested priority: P0. Type: infrastructure.
Published issue: [#6](https://github.com/ozdemirr1/opsdesk/issues/6).

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.

**Goal:** Establish isolated PostgreSQL test infrastructure with a restricted target,
reliable session management, and isolation between test scopes.

**Scope:**

- Synchronous SQLAlchemy engine/session-factory setup with separate application
  and integration-test configuration; explicit cleanup and transaction ownership.
- Exact test-database and permitted server-target validation.
- Isolation compatible with application commits and exceptions.
- Database credentials supplied through environment configuration.

**Out of scope:** Business schemas, their migrations/tests, domain repositories,
business transaction workflows, CI/CD, and Docker Compose.

**Acceptance criteria:**

- Integration tests accept only the exact database name opsdesk_test.
- Reject opsdesk_dev and every other name, including another_test.
- Restrict the allowed server target explicitly; a database name alone is insufficient.
- Validate the target before any destructive setup or cleanup.
- Cleanup still runs when the test body raises an exception.
- Exclude passwords and full connection URLs from application logs, error output,
  and surfaced exception traces.
- README documents local PostgreSQL provisioning and guarded test execution.

**Expected tests:**

- Rejected targets raise an error and never reach destructive setup/cleanup functions.
- A controlled verification exercises two successive isolated scopes: a record in a
  test-only probe table from the first is absent in the second.
- Verification is independent of business schemas and test execution order.
- Simulated connection failure exposes neither a synthetic password nor full URL
  in captured application logs or error output.

**Dependencies:** Backend application foundation.

**Selected isolation policy (Sunday):**

- Run one test suite at a time against the designated database; tests are sequential.
- Allow actual application commits and verify their effects through independent sessions.
- Validate exact database/server targets before any destructive setup or cleanup.
- Clean before and after test scopes using explicit DELETE statements on a fixed
  table allowlist, in foreign-key-safe order, in a separate committed transaction.
- Preserve migration history. At this stage use only a probe table; later schema
  issues extend the allowlist with their business tables.
- Roll back unfinished test transactions as needed and close sessions before cleanup.
- Attempt teardown after ordinary test exceptions. Surface cleanup errors alongside
  the original failure and stop further scopes when cleanup cannot restore isolation.
- Process termination may prevent teardown; validated startup cleanup handles leftovers.
- Controlled concurrency tests may use multiple connections inside one test; wait
  for their completion before cleanup. This does not authorize overlapping test runs.
- App configuration may legitimately target development; test-only target restrictions
  must not be applied indiscriminately to normal application configuration.

**Additional verification:** A committed probe write is readable from a separate
session and absent in the next scope; repeat with a test-body exception. Verify
session/connection release, rejected-target non-invocation of destructive functions,
and stopping after cleanup failure. No business schema or migrations belong here.
