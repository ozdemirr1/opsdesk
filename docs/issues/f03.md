# Implement login and access-token issuance

Suggested priority: P0. Type: feature.

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for

## Goal

Authenticate active global Users and issue the reviewed access token.

## Scope

- POST /auth/login; only email/password, canonical lookup, safe library password verification, current active-state check.
- Maintained JWT library and server-controlled signing configuration; reuse password policy/configuration compatible with registration.

## Out of scope

- Registration, refresh/MFA/reset/email, protected-request token verification, Organization authorization.

## Acceptance criteria

- Invalid inputs produce 422; valid credentials for an active User produce 200 with access_token and token_type=bearer.
- Subject, signature, claims, expiration, and issuer/audience follow D02. No manual cryptography.
- Unknown email/wrong password/inactive account share 401 unauthenticated for otherwise valid requests; no token issuance on rejection.
- No User/Organization/Membership creation. Logs and errors exclude tokens and secrets; unexpected persistence/signing failures produce no success.
- Apply reviewed timing-discrepancy mitigation without asserting exact equal request durations.

## Expected tests or review evidence

- Success including token signature/claims, normalized email equivalence, controlled time/settings.
- Same public error for each credential/account failure; token issuance is not invoked.
- Invalid/extra inputs, no new identities, safe logs, simulated DB/signing failure.

## Implementation evidence — 28 September 2026

The feature branch implements strict `POST /auth/login` input, shared canonical email
and NFC password handling, SQLAlchemy User lookup, maintained Argon2id verification,
generic credential rejection, and maintained-library HS256 access-token issuance.
The signing secret is environment-backed with no default. Issued tokens contain only
the five reviewed claims and use an injected UTC clock for deterministic tests.

Unit and HTTP tests cover service ordering, dummy-hash verification for unknown Users,
inactive/wrong-password rejection, no issuance after rejection, safe 401/422/500
responses, signing/repository failures, exact claims and application lifecycle wiring.
The focused regression passed 122 tests. Four PostgreSQL tests then verified a real
stored hash and canonical lookup, signature/claims at controlled time, identical public
credential failures, and no User/Organization/Membership creation. Full regression,
hosted CI, PR review, merge and issue closure remain pending.
