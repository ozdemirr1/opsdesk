## Goal

Expose only Tickets within the caller's reviewed Organization and requester visibility.

## Scope

- GET /organizations/{organization_id}/tickets and GET /organizations/{organization_id}/tickets/{ticket_id}.
- Status/priority/assignee filters, finalized queue-filter inclusion, pagination and TicketResponse.

## Out of scope

- Creation, mutations, Comments, cursors or snapshot guarantees not chosen in D03.

## Acceptance criteria

- Active User/membership/Organization required. Customers see only requested-by-self Tickets; staff see all within the Organization. All lifecycle states remain readable.
- Missing, foreign-path, or invisible Ticket detail uses 404 ticket_not_found after shared guards.
- Apply scope and filters before created_at DESC, ticket_id DESC and pagination. Counts use identical scope/filters without limit/offset.
- Use the standard envelope, limits, empty-list behavior and D03 count consistency. Filters cannot widen customer visibility.
- No updates or implicit workflow permissions are granted by reading.

## Expected tests or review evidence

- Customer-own versus other requester; staff visibility; foreign tenants, missing Tickets, inactive actor/Organization.
- Scoped counts/filters, same-timestamp tie breaking, page bounds, no matches and offset beyond matches.
- Any included unassigned filter and conflicts follow D03; safe detail/list projections and unchanged state.

## Week 15 implementation preparation — 23 October 2026

Planning only; list/detail endpoints are not implemented by this note.

### Endpoints and visibility

- GET /organizations/{organization_id}/tickets
- GET /organizations/{organization_id}/tickets/{ticket_id}

Require an active authenticated User, active Organization and active
membership under the shared access rules.

Customers can read only Tickets they requested.
Agents, admins and owners can read Tickets within their Organization.
Client filters must never widen this visibility.

After the shared guards, missing, foreign-Organization or invisible
Ticket details return 404 ticket_not_found.

### Collection contract

Follow docs/api-contract.md:

- Filters: status, priority, assignment and assignee_membership_id.
- Reject assignment=unassigned combined with assignee_membership_id.
- Default limit: 20; allowed range: 1..100.
- Default offset: 0; minimum: 0.
- Reject invalid, repeated and unknown query parameters.
- Apply visibility and filters before pagination.
- Order by created_at DESC, ticket_id DESC.
- Return items, total_count, limit and offset.
- Count and items must use the same scope, filters and database snapshot.
- An offset beyond the matching records returns empty items with the
  unchanged matching total_count.

Title search is not part of the reviewed backend contract.
Do not advertise filtering one downloaded page as a search across all
Tickets. Review server-side search separately before adding that claim.

### Frontend integration boundary

- Obtain the selected Organization from API-backed membership context.
- Pass the in-memory access token through the existing API boundary.
- Map TicketResponse into the frontend display model explicitly.
- Provide loading, safe error, empty-list and not-found states.
- Clear previous Organization data when the selected Organization changes.
- Ignore or abort responses belonging to an earlier Organization/session.
- Keep fixture-backed screens clearly labelled until integration is verified.

### Required backend evidence

- Customer sees own requested Tickets and cannot read another customer's.
- Staff visibility remains bounded to the selected Organization.
- Foreign-Organization Ticket IDs cannot bypass the path scope.
- Inactive User, membership and Organization are rejected.
- Filters and total_count preserve the same visibility rules.
- Ordering is deterministic when created_at values are equal.
- Invalid pagination and contradictory filters are rejected.
- Empty results and offsets beyond matches return the agreed envelope.
- Reads do not modify Ticket state.

Use only the guarded product database `opsdesk_product_test` for destructive
integration tests. Never target product development or hosted demo databases;
`opsdesk_test` belongs to the historical Month 02 learning API.


## Week 15 implementation breakdown — 24 October 2026

The frontend adapter is implemented in `frontend/src/api/tickets.ts` with unit
tests. The table still consumes labelled fixtures. The following access and
integration work is planned, not implemented by the adapter.

### Organization context and visibility review

| Situation | Planned Ticket-read behavior |
| --- | --- |
| Active customer membership | Only rows whose requester_membership_id matches the current membership |
| Active agent/admin/owner membership | All visible rows within the selected Organization |
| Missing/inactive membership or foreign tenant | Deny access under the shared guards; never broaden the query |
| Suspended Organization | Basic Organization information may be listed, but Ticket access is denied |
| Visible Ticket in resolved/closed state | Read allowed; read permission grants no mutation rights |

Use the existing GET /organizations response's `organization` and
`own_membership` pair for selection context. Do not infer roles from the global
User or from a client-selected role. The backend rechecks current membership.
An account can have different roles in different Organizations.

Distinguish these UI states: no memberships, suspended Organization, no Tickets
in an active Organization, no matching Tickets, loading, and request failure.
An error must not be rendered as a successful empty list. Changing Organization
must reset filters, page offset and selection, clear old data, and invalidate
pending responses. Signing out must invalidate pending requests as well.

### Adapter boundary

`TicketResponse` mirrors the existing backend response fields; timestamps are
JSON strings and an unassigned assignee is null. `toTicketSummary` selects
ticket_id (renamed ticketId), title, status, priority and description. It does
not mutate its input, fetch data, authorize access or validate unknown JSON.

Before wiring HTTP responses, add runtime validation at the API boundary for
the envelope and each item. In particular, PostgreSQL bigint exceeds JavaScript's
safe-integer range: reject nonpositive/unsafe parsed numeric IDs rather than use
a rounded value. The mapper assumes validated data. Supporting the full bigint
range with string IDs requires a separately reviewed wire-contract change.

### Small implementation packages

1. Input/output contract: add Ticket list query/envelope schemas and query
   dependency. Test bounds, duplicate/unknown keys and assignment conflicts.
   Reuse the reviewed pagination behavior without changing Organization APIs.
2. Scoped reads: add read repository/service contracts alongside creation code;
   implement SQL reads in `src/opsdesk/db/repositories/tickets.py`. Share the
   visibility predicate between list, count and detail. Count/items use one
   snapshot (one SQL statement or a short read-only REPEATABLE READ transaction).
   Do not copy mutation locking into reads without a demonstrated need.
3. HTTP endpoints: add GET list/detail routes and dependencies, explicit error
   translation and TicketResponse projections. Test authentication, shared guard
   precedence, hidden/foreign detail 404, empty pages and rejected query values.
4. PostgreSQL evidence: use guarded `opsdesk_product_test` fixtures for two Organizations, customer
   and staff memberships, other requesters, inactive states, timestamp ties,
   filters/counts and beyond-end offsets. Verify count/items snapshot consistency
   under concurrent writes and unchanged business state after reads/rejections.
5. Frontend integration: validated Organization/Ticket API boundaries, explicit
   Organization selection, API-to-display adapter, loading/error/empty states,
   server pagination and stale-response cancellation tests. Replace fixture data
   only after the real endpoint behavior is verified. Title search needs its own
   server contract; do not silently search only the current page.

Planning estimate: packages 1–4 need roughly 2–3 focused sessions including
database verification; package 5 needs another 1–2. These are provisional learning
estimates, not a Sunday completion promise. Re-estimate after the first package.
Comments, role mutations, UI redesign and deployment are outside these packages.
