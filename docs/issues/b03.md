# Create the initial identity and organization schema

Local planning ID: B03. This is not a GitHub issue number.

Suggested priority: P0. Type: schema.
Published issue: [#7](https://github.com/ozdemirr1/opsdesk/issues/7).

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.

## Goal

Apply the reviewed Users, Organizations, and Memberships schema with Alembic and PostgreSQL constraint verification.

## Scope

- Initialize Alembic for synchronous connection configuration. Create separate persistence models and migrations.
- Implement bigint GENERATED ALWAYS AS IDENTITY primary keys, required columns/defaults, email uniqueness, role CHECK, and ON DELETE RESTRICT foreign keys.
- Implement UNIQUE(user_id, organization_id), UNIQUE(organization_id, membership_id), and the partial unique active-owner index.

## Out of scope

- Authentication and Organization-creation workflows, Ticket/Comment/Attachment tables, implementing the at-least-one owner rule via this index.

## Acceptance criteria

- Upgrade, downgrade, and re-upgrade work only against the guarded test target. Run schema-changing tests separately and restore the expected schema before data tests. Stop on restoration failure.
- Canonical email and membership-pair uniqueness follow the reviewed contracts; membership uniqueness includes inactive rows.
- Role vocabulary, NOT NULL, defaults, and FK deletion behavior match the relational model.
- At most one active owner per Organization is enforced; zero active owners and multiple inactive owners for distinct Users are structurally possible, not authorized application workflows.

## Expected tests or review evidence

- Duplicate canonical emails, invalid roles/null fields, initial active defaults, duplicate User-Organization pairs including inactive existing rows.
- Deletion of referenced Users/Organizations fails. Second active owner fails; inactive owners for distinct Users and zero active owners demonstrate constraint limits.
- Guarded upgrade/downgrade/re-upgrade and schema restoration; integrate new tables into test cleanup allowlist.
