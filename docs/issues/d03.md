Local planning ID: D03. This is not a GitHub issue number.

Suggested priority: P0. Type: design.
Published issue: [#3](https://github.com/ozdemirr1/opsdesk/issues/3).

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for

Status: awaiting user review; not implemented or published.

## Goal

Close the remaining bounded contract gaps so endpoint work does not invent behavior during implementation.

## Scope

- Organization name/response and membership/Comment input limits; list ordering/projections/filters and count/items consistency.
- Error envelopes and failure precedence, no-op cases, timestamp policy, and remaining transport/server-error behavior.
- Record Attachment migration timing explicitly without adding metadata APIs. Define safe request-log/correlation-ID expectations for Q02.

## Out of scope

- Implementation, new product capabilities, changing approved role/lifecycle rules without separate review.

## Acceptance criteria

- Document exact non-Ticket string bounds, normalization and accepted body/query fields; preserve already-reviewed defaults and scopes.
- Choose Organization/membership/comment ordering and count/items snapshot policy. Decide assignment queue and assignable directory query inclusion/semantics and contradictory-filter errors.
- Finalize nested Organization creation/list and ownership-transfer responses and error details/field paths.
- Specify duplicate/active reactivation, repeated role/assignment/deactivation requests, missing/foreign member targets and overlapping-failure precedence. Preserve reviewed no-op matrix and fixed outcomes.
- Decide malformed JSON/unsupported media-type and unexpected-error mappings without confusing framework defaults with product decisions.
- Select updated_at expression and which business mutations affect it; no-ops preserve it. Define request correlation fields and safe handling of user-supplied correlation values.
- Record Attachment migration inclusion/deferment as a release decision; domain retention does not imply executable table or endpoint.

## Expected tests or review evidence

- Reviewed request/response examples and decision tables for every listed gap; no TBD left for a dependent issue claiming ready to implement.
- Cross-check against D01/D02 to avoid conflicting validators or duplicate email policies. No application tests required to finish design.

## Reviewed partial decision — 17 September 2026

Furkan accepted the [Organization name contract](../api-contract.md#organization-name-contract):
required string, Python edge trimming, 1..255 Unicode code points after trimming,
preserved case/internal spaces, no additional Unicode normalization, and rejection
of NUL/LF/CR/TAB before trimming. Names are not unique. The initial schema uses a
required text column with the reviewed length bounds; application normalization
and any additional database whitespace guards have the distinct limits documented
in the contract.

This resolves the name-bound prerequisite for B03 only. Other D03 decisions remain
open; this note does not claim endpoint implementation or GitHub issue closure.

## Reviewed shared-error subset — 18 September 2026

Furkan accepted the [shared error/logging contract](../error-logging-contract.md):
consistent envelope, empty non-field details, safe field paths/messages, 400/415
transport behavior, safe 500 and framework errors, required headers, server-issued
request IDs, and bounded route-template diagnostics. This supplies #10's shared
error/logging decisions. It does not close #3's remaining feature contracts or

## Reviewed fields and response subset — 24 September 2026

Furkan accepted the remaining Comment/membership request-field rules and the nested
Organization/ownership response structures in the
[API contract](../api-contract.md). Comment content supports normalized multiline
text with a 1..10000-code-point bound; membership email reuses the shared identity
policy; roles and positive membership identifiers use strict endpoint-specific
fields. Server-derived identity, role/default state, timestamps, and relationships
remain forbidden request fields.

Organization creation/list items now use named `organization` and `own_membership`
projections. Ownership transfer returns named post-commit previous/new owner
membership projections without global User data. This completes D03's field-bound
and nested-response group. Collection/filter/count, repeated-operation and error
precedence, timestamp policy, and Attachment migration timing remain open.

## Reviewed collection policy — 26 September 2026

Furkan accepted the collection, filtering and count/items policy in the
[API contract](../api-contract.md). Organizations and memberships use stable ascending
IDs; Comments use chronological created_at/comment_id order; Tickets retain descending
created_at/ticket_id order. Every collection uses the common bounded offset envelope.

Ticket assignment filters now distinguish assigned/unassigned explicitly and reject
the contradictory unassigned-plus-assignee combination. The membership directory
supports role, active-state and computed assignability filters with explicit
contradiction rules. Valid missing/foreign filter targets produce empty scoped results
rather than existence disclosures. Filters never widen requester or tenant visibility.

Within one response, count and items use one PostgreSQL snapshot, either
through one statement or a short read-only REPEATABLE READ transaction. This guarantee
does not extend across separate offset-page requests. This completes D03's
collection/filter/count group. Repeated-operation and business-error precedence,
timestamp policy, and Attachment migration timing remain open.
