# Finalize identity validation and authentication contracts

Local planning ID: D02. This is not a GitHub issue number.

Suggested priority: P0. Type: design.
Published issue: [#2](https://github.com/ozdemirr1/opsdesk/issues/2).

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.

## Goal

Make identity inputs, email uniqueness, passwords, login outcomes, and token validation unambiguous before implementation.

## Scope

- Define email canonicalization and storage/uniqueness rules shared by registration, login, and exact-email member addition.
- Define password bounds, length units, accepted characters, Unicode handling, and explicit normalization without silent trimming/truncation.
- Define registration/login/current-user inputs, response projections, duplicate-registration errors, JWT claims and signing/validation policy.

## Out of scope

- Endpoint implementation, refresh tokens, MFA, password reset, email delivery.

## Acceptance criteria

- Document exact field limits, invalid/extra/missing input behavior, canonical-email examples, and duplicate-registration status/code.
- Otherwise valid login with unknown email, wrong password, or inactive account uses the same public 401 unauthenticated response. Describe timing-discrepancy mitigation without promising identical times.
- Successful login returns access_token and token_type. Define subject as immutable User ID, permitted algorithms, required claim types, expiration, and issuer/audience policy.
- Require current persisted active User on each protected request after token validation. Global authentication does not grant Organization permissions.
- Exclude passwords, hashes, secrets, raw tokens, SQL and traces from error output/logs. The successful login token is an intentional response exception.

## Expected tests or review evidence

- Reviewed valid/invalid/boundary registration and login examples; duplicate canonical emails.
- Protected-request examples for malformed/expired tokens, invalid signatures/claims, missing or inactive current User. These are not login request token tests.
- Recorded policies block affected schema and endpoints; this design issue does not execute tests.

## Dependencies

- Reviewed Week 09 baseline; no implementation-issue prerequisite.
