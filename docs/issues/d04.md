# Define coordinated transaction and concurrency rules

Local planning ID: D04. This is not a GitHub issue number.

Suggested priority: P0. Type: design.
Draft origin: grouped Sunday proposal based on reviewed product rules.
Status: awaiting user review; not implemented or published.

## Goal

Define a concrete protocol that keeps authorization and ownership/assignment invariants valid under overlapping operations.

## Scope

- Transaction owners, lock targets/order, re-check points, constraint-error mapping and bounded retry/conflict policy.
- Organization creation/owner transfer, membership addition/role/deactivation, Ticket creation/claim/reassignment/reopening and Comment posting/closing.

## Out of scope

- Executable locking implementation, async SQLAlchemy, distributed locks, Redis, new deactivation/suspension endpoints.

## Acceptance criteria

- Enumerate competing operations and show which state is protected, when it is reread, and when the transaction commits.
- Choose one cooperating protocol and global lock order; explain how new rows and registration unique conflicts are handled.
- Owner transfer ordering works with the partial unique index and preserves exactly-one committed owner with an active User.
- Assignment/eligibility changes and reopen/close/post operations cannot pass stale authorization or state checks.
- Document global User/Organization state-change coordination as a future integration obligation; no deferred endpoint is added now.
- Specify externally observable errors/retries with D03 and how controlled concurrency tests force overlap without relying on sleeps.

## Expected tests or review evidence

- Interleaving walkthroughs for two claims, two transfers, role/deactivation versus assignment, and closing versus comment creation.
- Rollback and deadlock/error handling expectations plus multi-session test plans. A transaction block alone is not accepted as the protocol.

## Dependencies

Reviewed Week 09 baseline; no implementation prerequisite.
