# Implement organization creation with initial ownership

Local planning ID: F05. This is not a GitHub issue number.

Suggested priority: P1. Type: feature.
Published issue: [#14](https://github.com/ozdemirr1/opsdesk/issues/14).

Snapshot of the initial published scope, 13 September 2026. Follow GitHub for
current status and scope discussion; this file is not a live progress tracker.

## Goal

Create an Organization and its initial owner membership atomically for an active global User.

## Scope

- POST /organizations; name validation; server-derived actor ownership; one explicit transaction.

## Out of scope

- Organization reads/rename/suspend/delete, adding others, ownership transfer, invitations/billing.

## Acceptance criteria

- Active global User suffices, including no existing memberships. No target membership or prior Organization role is required.
- Only name is accepted; extra IDs/roles/active fields produce 422. Names are not globally unique.
- Create active Organization plus active actor owner membership together; return finalized nested projection with 201 only after commit.
- Failure persists neither new record and changes no pre-existing identities/memberships. Missing/invalid/inactive authentication returns 401.
- Coordinate current User state with conflicting changes through D04, not a stale pre-check alone.

## Expected tests or review evidence

- User with no memberships and any role in another tenant can create; duplicate valid display names allowed.
- Correct ownership and active state; invalid fields/authentication denied.
- Failure between Organization and membership writes and at commit leaves no partial state, checked with fresh session.

## Implementation checkpoint — 1 October 2026

The `feature/week-12-organization-creation` branch contains:

- strict Organization-name normalization and a request schema that rejects
  client-selected User, role, and active-state fields;
- separate domain, repository, service, persistence, dependency, and transport
  responsibilities;
- actor User locking with transaction-local `lock_timeout = '2s'`, followed by a
  fresh active-state check;
- one service-owned transaction for the Organization and initial owner membership;
- translation of only PostgreSQL 55P03, 40P01, and 40001 into the fixed
  `503 concurrency_busy` response;
- safe `201` output that excludes password data and membership `user_id`; and
- a full non-integration snapshot of 283 passed tests with 141 database/schema
  cases deselected.
