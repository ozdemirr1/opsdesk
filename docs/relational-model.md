# Relational Model

Relational baseline: Week 09 Wednesday, 9 September 2026.
Policy alignment: Thursday, 10 September 2026.

This document translates the [domain model](domain-model.md) into a proposed
PostgreSQL schema. The [ERD](erd.md) illustrates the relationships. It is design
documentation, not an executable migration or proof that constraints have been tested.
The [access-control matrix](access-control.md) and [Ticket lifecycle](ticket-lifecycle.md)
supply reviewed operation rules. Remaining validation and workflow decisions are
listed at the end.

## Conventions

- Each table uses a bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY. IDENTITY
  generates values; the primary key enforces unique identity. Identity generation
  does not make arbitrary SQL changes impossible. Normal application operations
  never accept or change technical identities.
- Textual fields use text; exact maximum lengths remain explicit validation work.
- All columns below are NOT NULL except tickets.assignee_membership_id.
- Memberships are retained on departure and reactivated on return, rather than
  replaced. Stable references do not constitute complete historical role/assignment logs.
- Every FK in this baseline uses ON DELETE RESTRICT, with default NO ACTION on
  referenced-key updates. FK validity alone does not enforce business immutability.
- Name constraints explicitly when implementing Alembic migrations.

## users

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| user_id | bigint | No | Identity primary key | Stable global account identity |
| email | text | No | UNIQUE; canonicalization policy pending | Normalized login identifier |
| password_hash | text | No | Generated by maintained password-hashing library | Local authentication; never plaintext |
| is_active | boolean | No | DEFAULT true | Global account state |

UNIQUE(email) alone is not a complete normalization or case-insensitive identity
policy. The intended lower-case canonical storage policy needs a precise application
normalization contract and matching database guard before migration implementation.
Syntax validation remains an application responsibility. Email is not a relationship key.

## organizations

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| organization_id | bigint | No | Identity primary key | Tenant identity |
| name | text | No | Nonblank text; limits pending | Non-unique display name |
| is_active | boolean | No | DEFAULT true | Organization state |

The field does not by itself define suspension or reactivation workflows. Active
Organization creation must establish the required owner in the same business
transaction; a default of true does not provide that guarantee.

## organization_memberships

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| membership_id | bigint | No | Identity primary key | Stable contextual identity |
| user_id | bigint | No | FK users(user_id) | Global account |
| organization_id | bigint | No | FK organizations(organization_id) | Tenant context |
| role | text | No | CHECK valid role; no privilege default | One organization-scoped role |
| is_active | boolean | No | DEFAULT true | Current membership state |

```sql
CHECK (role IN ('owner', 'admin', 'agent', 'customer'))
UNIQUE (user_id, organization_id)
UNIQUE (organization_id, membership_id)
```

These are constraint fragments, not a complete CREATE TABLE statement. The first
UNIQUE is the business rule and includes inactive records. The second provides an
explicit composite FK target, even though membership_id is independently unique.
The application assigns roles through authorized workflows, not unrestricted client input.

### Owner Enforcement

```sql
CREATE UNIQUE INDEX uq_memberships_active_owner_per_org
ON organization_memberships (organization_id)
WHERE role = 'owner' AND is_active = true;
```

This limits each Organization to at most one active owner membership, including
inactive Organizations. It permits zero owners and does not check users.is_active.
The index is not a deferred unique constraint: a transfer cannot temporarily create
two active owners and rely on commit-time validation.

Application transactions must preserve the stronger active-Organization rule:
exactly one active owner membership belonging to an active User. A candidate transfer
sequence is to lock the Organization, re-read and validate current state, demote the
old owner to admin, promote the eligible active admin member, validate, then commit together.
Failure rolls back both changes. All ownership-affecting workflows must cooperate
with the same concurrency protocol; wrapping separate checks and writes in a
transaction is not sufficient on its own. Coordination with global User deactivation
and a consistent lock order remain implementation prerequisites.

## tickets

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| ticket_id | bigint | No | Identity primary key | Stable request identity |
| organization_id | bigint | No | FK organizations(organization_id) | Fixed tenant boundary |
| requester_membership_id | bigint | No | Composite membership FK | Fixed requester attribution |
| creator_membership_id | bigint | No | Composite membership FK | Fixed creator attribution |
| assignee_membership_id | bigint | Yes | Composite membership FK | Optional current assignment |
| title | text | No | Nonblank text; limits pending | Short issue summary |
| description | text | No | Nonblank text; limits pending | Detailed support request |
| status | text | No | CHECK valid status; DEFAULT 'open' | Current lifecycle state |
| priority | text | No | CHECK valid priority; DEFAULT 'medium' | Urgency level |
| created_at | timestamptz | No | DEFAULT now() | Creation transaction time |
| updated_at | timestamptz | No | DEFAULT now(); explicit refresh on updates | Last application modification timestamp |

```sql
CHECK (status IN ('open', 'in_progress', 'resolved', 'closed'))
CHECK (priority IN ('low', 'medium', 'high', 'urgent'))
UNIQUE (organization_id, ticket_id)
```

Title is not unique. Repeated titles and multiple requests by one member are allowed.
Status vocabulary does not enforce valid transitions, caller permissions, or the
creation status. The API derives both creator and requester from the authenticated
User's current active membership for every permitted creator role. Creation starts
open and unassigned; client-supplied assignment is rejected. Omitted priority defaults
to medium; explicit null and invalid values are rejected. Assignments require an
active User and active same-Organization agent/admin/owner membership. In_progress
requires an eligible assignee; exact additional database enforcement remains part of
migration design, not a guarantee supplied by the current status CHECK.

The nullable assignee FK uses default MATCH SIMPLE. With a non-null organization_id
and null assignee_membership_id, this FK requires no membership match. The separate
Organization FK still enforces a valid tenant. MATCH FULL would reject that mixed
null/non-null pair and is not appropriate for this design.

### Time and Immutable Fields

Defaults apply on insertion; updated_at does not refresh automatically. Application
persistence updates must explicitly refresh it when Ticket fields change. The exact
update-time expression and tests will be chosen before implementing persistence.
PostgreSQL now() represents transaction start, not wall-clock commit time, and does
not advance within one transaction. Timestamps alone are not a strict revision counter.

Normal updates cannot change organization_id, requester_membership_id,
creator_membership_id, or created_at. The FKs do not prevent replacement with a
different valid same-Organization membership. Application boundaries must enforce
this immutability; stronger database enforcement would require a separate decision.

## comments

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| comment_id | bigint | No | Identity primary key | Message identity |
| organization_id | bigint | No | Shared by both composite FKs | Tenant consistency |
| ticket_id | bigint | No | Composite Ticket FK | Fixed parent |
| author_membership_id | bigint | No | Composite membership FK | Fixed author attribution |
| content | text | No | Nonblank text; limits pending | Conversational message |
| created_at | timestamptz | No | DEFAULT now() | Creation transaction time |

There is no updated_at: user-facing comments are append-only. No normal application
endpoint, service, or repository operation edits/deletes them. This policy includes
admin and owner. Existing constraints do not independently prevent direct SQL edits
or deletion of the Comment itself. Organization, Ticket, author, content, and created_at
remain fixed through normal application operations.

Author is derived from authenticated identity. User, membership, and Organization
must be active, with separate permission checks for Ticket reading and Comment posting.
Reading follows Ticket visibility; there is no internal-note tier in Month 03.
Posting is permitted only in open/in_progress/resolved under the role/resource rules.
Comments in closed remain readable but new comments are denied.

## attachments

This is a planned metadata model. It does not create an upload endpoint, establish
a storage provider, or promise physical file availability.

| Column | Type | Nullable | Constraint / default | Purpose |
| --- | --- | --- | --- | --- |
| attachment_id | bigint | No | Identity primary key | Metadata identity |
| organization_id | bigint | No | Shared by both composite FKs | Tenant consistency |
| ticket_id | bigint | No | Composite Ticket FK | Fixed parent; no Comment link |
| uploader_membership_id | bigint | No | Composite membership FK | Submission attribution |
| filename | text | No | Nonblank text; limits pending | Untrusted display filename, not a storage path |
| file_size_bytes | bigint | No | CHECK (file_size_bytes > 0) | Declared positive byte count |
| mime_type | text | No | Nonblank text; syntax policy pending | Untrusted content-type label |
| created_at | timestamptz | No | DEFAULT now() | Metadata creation transaction time |

Duplicate filenames are allowed. Rejecting zero-byte declarations is the selected
initial product policy, not an inherent limitation of files. Actual size, type,
upload success, and storage availability are not proven by these fields. Maximum
size, type allowlists, inspection, metadata updates, and physical cleanup belong to
the future upload workflow. Submission must eventually derive the attributed member
from authenticated identity and require active User/membership/Organization plus
Ticket visibility and explicit attachment permission.

## Foreign Key Inventory

Every row uses ON DELETE RESTRICT. No child FK columns below are nullable except
assignee_membership_id; that FK intentionally uses MATCH SIMPLE as described above.

| Source table | Source columns | Target table | Target columns |
| --- | --- | --- | --- |
| organization_memberships | (user_id) | users | (user_id) |
| organization_memberships | (organization_id) | organizations | (organization_id) |
| tickets | (organization_id) | organizations | (organization_id) |
| tickets | (organization_id, requester_membership_id) | organization_memberships | (organization_id, membership_id) |
| tickets | (organization_id, creator_membership_id) | organization_memberships | (organization_id, membership_id) |
| tickets | (organization_id, assignee_membership_id) | organization_memberships | (organization_id, membership_id) |
| comments | (organization_id, ticket_id) | tickets | (organization_id, ticket_id) |
| comments | (organization_id, author_membership_id) | organization_memberships | (organization_id, membership_id) |
| attachments | (organization_id, ticket_id) | tickets | (organization_id, ticket_id) |
| attachments | (organization_id, uploader_membership_id) | organization_memberships | (organization_id, membership_id) |

The same child organization_id participates in both child FKs. A valid Ticket ID
alone and a valid membership ID alone would not prove they belong to the same tenant.
Separate direct Organization FKs on comments/attachments are unnecessary for existence:
their non-null composite Ticket FK already leads to a Ticket with a valid Organization.

## Deletion and Authorization Boundaries

- Memberships block deletion of referenced Users and Organizations.
- Tickets block deletion of referenced Organizations and participant memberships.
- Comments and Attachment metadata block deletion of referenced Tickets and memberships.
- These incoming references do not prohibit deleting an unreferenced parent, or a
  child itself. Endpoint/service policies still restrict which deletion operations exist.
- Deactivation changes state without deleting rows. Anonymization does not remove
  foreign-key references, and historical attribution is not reassigned to permit deletion.
- Physical file cleanup, retention, and eventual erasure workflows remain undesigned.
- Existence/tenant consistency is not authorization: current User state, active
  membership/Organization, eligible roles, and resource permissions need application checks.
- CHECKs restrict allowed values, not transitions. FKs preserve links, not current
  role eligibility. Active-work assignments require the reviewed handover policy.

## Text Validation Baseline

The proposed nonblank guard for names, titles, descriptions, comments, filenames,
and MIME labels is a NOT NULL column with a CHECK such as:

```sql
CHECK (content ~ '[^[:space:]]')
```

This requires a character outside PostgreSQL's whitespace class. Plain trim(content)
without an explicit character set only removes ordinary spaces, not every whitespace
character. POSIX character-class handling outside ASCII depends on locale/collation;
the application and database normalization contracts require shared test examples.
Nonblank does not imply valid MIME syntax, valid email, safe filenames, or bounded size.
Exact maximum lengths are still open and must be resolved before the relevant schema
and API validation are implemented.

## Remaining Design Work

- Define email normalization/storage checks and exact string length limits.
- Translate the reviewed matrices into migration and service checks; priority
  defaults to medium, assignment at creation is forbidden, and in_progress requires
  an eligible assignee. No new constraints have been applied.
- Complete API operation coverage and same-value update/error behavior.
- Specify the cooperating transaction/lock protocol and lock order for ownership,
  assignment, membership changes, and global account deactivation.
- Define the updated_at update expression and verification expectations.
- Review access-pattern indexes after endpoint/pagination contracts; avoid adding
  speculative indexes. PostgreSQL does not automatically index referencing FK columns.
- Keep attachment storage operations, retention, suspension, and erasure workflows
  explicitly separate from the current structural baseline.

Future migration/integration checks must exercise invalid roles/statuses, duplicate
memberships, a second active owner, zero-owner application rejection, foreign-tenant
participants, unassigned Tickets, restricted parent deletion, and whitespace inputs.
These checks have not been executed. The complete Week 09 gate still precedes CRUD.
